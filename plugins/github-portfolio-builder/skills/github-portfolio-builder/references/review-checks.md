# Review checks

Use the checks that fit the target. Report only observations supported by the inspected sources.

## Profile and discovery

- Is the bio specific about the person's work and intended audience? Do profile links resolve?
- Is there a profile README? Does it lead with original, representative work and explain the person's role?
- Distinguish repositories explicitly pinned on the profile from GitHub's automatically shown popular repositories. Distinguish original repositories from forks or contributed work.
- Are descriptions and topics useful for discovery? Do they match the work shown?

## Repository and reuse

- Can a first-time visitor understand the problem, intended audience, creator's role, approach, and result from the README?
- Are setup, prerequisites, data assumptions, and limitations clear enough for the claimed level of reuse?
- Are examples or fixtures safe to publish and clearly fictional or anonymized? Do not call a sample importable or executable without checking it.
- Do linked demos and documentation resolve? A deck, screenshot, recording, source file, and live deployment establish different things. Verify the type and content of each before citing it.
- Check a supposed omission at a direct file path or complete repository tree. If only a partial page rendered, mark the omission unresolved.
- For a recording, inspect the actual media before stating its length, timestamps, or visible contents. Public video frames can still expose names, records, or browser addresses.

## Claims, rights, and privacy

- Verify numbers, field counts, behavior, and outcomes against the source most directly able to support them. A number or outcome on an owner-controlled page is **reported** until independently checked; inspecting the page verifies its presence, not the claim itself.
- Keep event or organization metrics separate from an individual's measurable contribution.
- Check whether a license covers the whole repository or only a named subdirectory or original materials. A contributor can grant rights only to material they own or can license.
- Preserve upstream licenses and attribution. Flag client, employer, student, applicant, credential, and internal system details before recommending public sharing.
- For a case study about client work, identify the person's role and any missing permission or redaction requirement. Suggest a generalized method or fictional example when direct publication is unsupported.

## Strong additions

Favor a concise case study, annotated architecture or workflow diagram, sanitized example, reproducible tutorial, or decision record when it adds evidence beyond what is already present. Each suggestion should name the visitor question it answers and the minimum source, permission, attribution, or disclosure check needed before upload.
